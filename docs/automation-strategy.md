# Automation strategy

Design baseline: 11 September 2026. Live authentication and checkout exploration is complete. The 15 selected scenarios are implemented, with the CHK-001 revision documented in observations.md. References below point to the implementation; execution evidence is reported separately. No design-first Git history is claimed.

## Selection and risk

The [test design](test-cases.md) selects 24 cases: **15 automated, 8 manual, 1 not applicable**. Purchase completion, valid account access and cart arithmetic are P0 because a failure blocks or misrepresents a transaction. Discovery, validation and empty-state recovery are P1. Secondary navigation and uncertain shared-environment behavior are P2. Selection favors observable business outcomes and independent setup over increasing test count.

Automation covers repeatable paths with a clear oracle: matching product identity, nonempty keyword/category results, correctly ordered numeric prices, cart totals, authentication transitions, required fields, the guest checkout gate and a completed practice order. Manual selection covers combinations, visual/keyboard quality, variable stock boundaries and recovery contracts that first need human investigation. There are no silently deferred selected cases: every selected case below has an explicit decision.

## Framework approach

Use TypeScript and Playwright Test with meaningful Page Object boundaries for catalog/product, cart/checkout and authentication/navigation as their interaction complexity warrants. Tests express business outcomes; page objects own stable locators and reusable actions. The live application uses `data-test`, so configure Playwright's test ID attribute accordingly. Prefer these explicit hooks, roles and associated labels; avoid generated product IDs, positional CSS and arbitrary sleeps.

Use typed JSON in `test-data/` for product choices, nonsecret synthetic profile, billing fields and stable expected messages where appropriate. Generate unique disposable identities/passwords at runtime or read credentials from local environment variables. Account fixture setup may use the application's API to reduce duplicated UI registration, provided registration itself remains a separately tested UI flow and the authentication under test is still performed through the UI. A cart fixture must create only that test's own cart. Each browser context is isolated; do not share mutable authenticated state files or depend on spec order.

Retain a small public-service load: modest worker count, bounded timeouts, no arbitrary sleeps and no loops that repeatedly create accounts until a test passes. Use locator assertions and, when needed, a specific response wait registered before the triggering action. If API setup or stock is unavailable, fail with a useful environmental diagnostic instead of masking it with a skip. Document any nonstandard waits or retries in observations. Clean up owned disposable data when the application exposes a supported safe mechanism; otherwise document that public practice accounts/orders remain disposable server-side records.

This is 51 planned project-case executions, not 51 distinct designed test cases. The configuration uses one retry for the shared public service; a failed first attempt that passes on retry is reported as flaky and does not create another designed test. Repeated failures remain failed. Report flaky outcomes explicitly rather than counting retry attempts as additional tests.

Generate an HTML report plus a terminal summary. Capture failure-only screenshots and retain failed traces and/or videos. Store generated results outside version control with `.gitignore`; traces may contain synthetic credentials, so do not publish unreviewed artifacts. README must explain installing browser binaries, selecting projects, running the suite, opening the HTML report and locating artifacts. A small checked-in text evidence summary may cite a real run's command, time, environment and results; never invent or promote unrun cases to passes.

## Baseline assumptions and exit criteria

The live Chromium UI was inspected on 11 September 2026 and displayed Toolshop v5.0 / build 2026-09-09. **Combination Pliers**, **Pliers**, search/reset and price sorting were present. Product details expose category, unit price and quantity controls. Registration and login forms are available; registration includes a required house-number field and a password rule requiring eight or more characters with uppercase, lowercase, a number and a special character. Address lookups can populate address fields, so verify the final synthetic values. Public product/brand data are mutable; comparisons derive current prices and do not freeze database IDs/counts. MCP confirmed cart quantity commits on blur and persists after reload. Checkout supports guest identity; signed-in synthetic Cash on Delivery uses two Confirm clicks and returns an invoice reference. See observations.md for evidence and the CHK-001 revision.

Implementation is ready for review when all 15 selected automated cases map to these IDs/titles; meaningful assertions and isolated fixtures are in place; all required projects have been attempted; failures have reproducible evidence and an explained cause; documentation states executed versus unexecuted/manual scope; no usable credentials or unnecessary generated output is committed; and the first meaningful commit demonstrates design before automation. Repository publication and submitting the repository link are separate delivery steps documented in the README.
